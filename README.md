# ХОКО Каталог — каталог, корзина и заказы из XLSX

![Каталог на компьютере](docs/catalog-desktop.png)

FastAPI/Starlette, SQLite, Jinja2 и обычный JavaScript. Магазин извлекает встроенные фотографии из XLSX, обновляет товары по штрихкоду, сохраняет корзину в браузере и пересчитывает цену заказа на сервере. Доступны поиск, фильтры, карточки товаров, ручная правка цен, импорт до 10 прайсов, админка, CSV и Telegram.

В Git не должны попадать `.env`, рабочая база, заказы, фотографии поставщика и прайсы. Файлы `docs/TEST_REPORT.md` описывают историческую проверку интерфейса; исходный security pass находится в [SECURITY_AUDIT.md](SECURITY_AUDIT.md), второй проход — в [SECURITY_AUDIT_R2.md](SECURITY_AUDIT_R2.md).

## Первый запуск

Поддерживаются Python 3.12 и 3.13. Для Docker нужен Compose 2.30+ (`env_file: format: raw` сохраняет символы `$` в Argon2-хеше). Одна копия `.env.example` недостаточна: шаблон не содержит готовых credentials.

Установите зависимости в отдельное окружение:

```bash
python -m venv .venv
# Linux/macOS:
. .venv/bin/activate
# Windows PowerShell вместо предыдущей строки:
# .\.venv\Scripts\Activate.ps1
python -m pip install --require-hashes -r requirements.txt
python scripts/setup_security.py --development
python app.py
```

Скрипт настройки запрашивает пароль скрытым вводом, создаёт стабильный случайный ключ и Argon2id-хеш в локальном `.env`; существующий файл без `--rotate` не перезаписывает. Пароль — минимум 16 символов, максимум 1024 UTF-8 байта, Unicode нормализуется в NFC. Ключ не генерируется заново при старте.

Открывайте `http://127.0.0.1:8000`; админка — `/admin`. Прямой запуск привязан к loopback. Windows: `start-local.bat` выполняет локальную настройку и запуск; `start.bat` и macOS `start.command` запускают локальный Docker Compose.

```bash
docker compose up --build
```

Локальный Compose явно выбирает development, отключает Secure для HTTP и публикует порт только на `127.0.0.1`. Production — режим по умолчанию; он прекращает запуск с пустыми/шаблонными/явно слабыми credentials, старым `ADMIN_PASSWORD`, невалидным Argon2id-хешем или отключённой Secure-cookie. Test выбирается явно в тестовой конфигурации с временной БД. Произвольный запуск Uvicorn с публичным bind в development не входит в поддерживаемый способ запуска.

## Публикация с доменом и HTTPS

1. Создайте production-конфигурацию: `python scripts/setup_security.py`. Для существующей установки выполните процедуру ротации ниже.
2. Укажите в `.env` настоящий `DOMAIN`, контакты магазина и реквизиты оператора. В `ALLOWED_HOSTS` для прямого запуска перечислите домен, `localhost`, `127.0.0.1`, без схем, портов и wildcard. Production Compose формирует этот список из `DOMAIN`.
3. Скопируйте `Caddyfile.example` в `Caddyfile`, направьте DNS на сервер и проверьте доступность портов 80/443.
4. Подготовьте права bind-mounted `data`: приложение использует UID/GID `10001:10001`. У этого пользователя должны быть права чтения/записи БД, её WAL/SHM и записи каталогов `data`, `media`, `imports`, включая существующие подкаталоги изображений. Сначала проверьте реальные абсолютные пути и владельцев именно этого проекта; не применяйте рекурсивный `chown` к домашнему каталогу или общему каталогу приложений. Для нового пустого дерева достаточно создать указанные каталоги с нужным владельцем. Старое дерево требует отдельной проверки прав; `chmod 777` не нужен.
5. Проверьте конфигурацию без вывода секретов и запустите:

```bash
docker compose -f docker-compose.prod.yml config --quiet
docker compose -f docker-compose.prod.yml up -d --build
```

Production Compose принудительно включает production и Secure, даже если в `.env` остались development-настройки. Порт приложения не публикуется. Caddy имеет адрес `172.30.93.2`, приложение — `172.30.93.3` в выделенной сети `172.30.93.0/29`; Uvicorn доверяет forwarding-заголовкам только от Caddy. Если эта сеть конфликтует с инфраструктурой, согласованно измените subnet, оба IP и `--forwarded-allow-ips`. Не используйте `*`. Дополнительные CDN/proxy требуют отдельной настройки доверия; приложение само не читает произвольный `X-Forwarded-For`.

Контейнер приложения: непривилегированный пользователь, read-only root, writable `data` и ограниченный tmpfs, удалённые capabilities, `no-new-privileges`, лимиты памяти/CPU/PID. Health-check обращается к `127.0.0.1:8000/healthz`. Проверьте реальный импорт после подготовки прав.

Access-логи Uvicorn и Caddy отключены, чтобы URL заказа, query-параметры и контакты не попадали в журналы. Caddy также отключает штатный runtime error log с URL запроса; это уменьшает диагностическую видимость. Пользовательские proxy/APM/логи хостинга нужно проверить отдельно. HSTS оставлен закомментированным: включайте его после проверки HTTPS; `includeSubDomains` и `preload` не включены.

## Ротация и административные сеансы

Для обновления существующей установки остановите все worker и сделайте резервную копию. Затем:

```bash
python scripts/setup_security.py --rotate
# Только для локального HTTP:
# python scripts/setup_security.py --rotate --development
```

Команда заменяет ключ и пароль, удаляет старый `ADMIN_PASSWORD`, сохраняет прочие настройки и не печатает credentials. Перезапустите все worker с одной конфигурацией. При изменении хеша или ключа сервер отзывает все административные сессии. Перестанут действовать и старые гостевые cookies; существующие заказы и ссылки `/order/{token}` сохранятся.

Административная cookie содержит случайный непрозрачный идентификатор, SQLite хранит его SHA-256 и сроки. По умолчанию: 30 минут простоя, 8 часов абсолютного срока, максимум 100 активных сеансов. Logout отзывает сохранённую копию cookie на сервере. Кнопка «Завершить все сеансы» отзывает все сеансы с проверкой CSRF. Флаг `admin_authenticated` из подписанной гостевой cookie не даёт полномочий.

## Каталог и XLSX

В админке выберите прайсы и коэффициент цены: `1.0` — исходная цена, `1.25` — наценка 25%. «Скрывать отсутствующие» допускается только с одним полным прайсом. Импорт по штрихкоду обновляет существующие товары без дублей. Административная исходная цена не попадает в публичный JSON/HTML.

Поддерживаются колонки `Модель`, `Цвет`, `Штрихкод`, `Шт. в кор.`, `Цена`, `Описание`, `Комментарий`, категории и обычные drawing anchors `oneCellAnchor`/`twoCellAnchor`. Реально декодируются PNG/JPEG/GIF/WebP; файлы с поддельным расширением и произвольные `.bin` отклоняются. Внешние связи, макросы и неподдерживаемые активные части книги запрещены. Необычные форматы «картинка в ячейке» могут потребовать отдельного адаптера.

```bash
python scripts/import_price.py "/путь/к/прайсу.xlsx" --multiplier 1.25
python scripts/import_price.py "/путь/к/полному-прайсу.xlsx" --deactivate-missing
```

Лимиты запроса: login 16 KiB, checkout/обычные формы 64 KiB, импорт 128 MiB вместе с multipart; до 10 файлов, каждый до 100 MiB, сумма файлов до 127 MiB. Login/checkout не принимают файлы. Форма ограничена 20 полями (импорт — 10); текстовое поле до 16 KiB, multipart дополнительно ограничивается заголовками парсера. Превышение бюджета возвращает 413, занятый импорт — 429/Retry-After. Одна web-загрузка допускается одновременно на все worker, CLI и фактический импорт используют общую вторую блокировку.

Приём тела дополнительно ограничен idle/total deadlines. По умолчанию обычная форма получает 30/180 секунд, импорт — 90/1800 секунд; total фиксирован на весь запрос и не продлевается каждым байтом. Параметры `FORM_BODY_IDLE_SECONDS`, `FORM_BODY_TOTAL_SECONDS`, `IMPORT_BODY_IDLE_SECONDS`, `IMPORT_BODY_TOTAL_SECONDS` находятся в `.env.example`. Caddy отдельно обрывает неполные заголовки через 10 секунд. Таймаут или преждевременное отключение до ответа дают 408, а открытые spool и upload-lock освобождаются.

| Ресурс XLSX | Бюджет |
| --- | --- |
| ZIP | 10 000 записей, 300 MiB распакованного размера, 32 MiB на запись |
| XML | 16 MiB на часть, 64 MiB суммарной работы чтения, 750 000 узлов, глубина 64 |
| Таблицы | 100 листов, 50 000 строк, 500 000 ячеек, 100 000 shared strings, 32 768 символов текста |
| Текст | 8 MiB хранимых shared strings, 32 MiB развёрнутых UTF-8 байтов по всем использованиям и листам; отдельные лимиты model/category/brand/color/box/description/comment/badge/sheet |
| Изображения | 2 000 штук; 10 MiB/файл, 150 MiB суммарно |
| Декодирование | 16 млн пикселей/кадр, 50 кадров, 32 млн пикселей на все кадры одного изображения, 500 млн на книгу |
| Работа | 60 секунд с проверками между ограниченными операциями |

Каждый файл импортируется отдельной атомарной транзакцией. Проверка/декодирование и запись временных изображений завершаются до `BEGIN IMMEDIATE`; writer-lock охватывает только быструю публикацию файлов и изменение каталога. Изображение не декодируется повторно внутри транзакции. Ошибка очередного файла не отменяет предыдущие успешно импортированные файлы из той же партии. Ошибочная транзакция удаляет только созданные ею новые изображения; общие и старые изображения сохраняются. Аварийное завершение процесса может оставить ограниченные бюджетом одного импорта неиспользуемые изображения; их очистка требует сверки с БД.

Новые архивы в `data/imports/managed-v1` ограничены 10 файлами, 256 MiB и 7 днями; очистка происходит при следующем импорте. Старые архивы вне этой области автоматически не удаляются. Успешные новые версии фотографий со временем увеличивают `media`: настройте мониторинг диска и проверяемую политику хранения.

## Заказы и уведомления

Цена, доступность, количество и сумма проверяются сервером; клиентские суммы игнорируются. Корзина содержит 1–50 уникальных целочисленных ID, количество 1–999 на позицию. Цена ограничена 100 млн рублей, сумма заказа — 10 млрд рублей; при превышении заказ не записывается. Невалидные поля дают контролируемый 4xx.

Страница checkout создаёт ключ повторной отправки. Повтор того же запроса в той же гостевой сессии возвращает тот же заказ; изменение содержимого при том же ключе даёт 409. Новый ключ означает новый осознанный заказ. Ключ без гостевой области не открывает чужой заказ. Заказ, позиции, запись ключа и задание уведомления фиксируются одной транзакцией. SQLite ждёт занятого writer не более 3 секунд; временная занятость возвращается как 503 с `Retry-After`, после чего безопасно повторить тот же ключ. Административный `last_seen` обновляется не чаще раза в минуту.

CSV истории заказов формируется потоково пакетами по 500 строк в отдельном DB-потоке. UTF-8 BOM, `;`, защита формул, авторизация и `no-store` сохранены; отключение клиента закрывает cursor/connection и не изменяет историю.

Для Telegram заполните `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в приватном `.env`. Отдельный ограниченный исполнитель забирает задания из SQLite, не блокируя event loop. Таймаут сети — 5 секунд, lease — 60 секунд; до 8 попыток с задержками 30 секунд–1 час. Ошибка отправки не откатывает заказ. После неопределённого сетевого результата уведомление может продублироваться: exactly-once доставка Telegram не гарантируется. Неотправленные после 8 попыток задания остаются со статусом `failed`; контролируйте их количество. Заказы, созданные при отключённом Telegram, имеют задание `disabled` и позднее автоматически не рассылаются.

Rate limiting хранится атомарно в SQLite: по умолчанию 20 login-запросов за 300 секунд и 60 checkout-запросов за 600 секунд на IP. Значения и окна задаются через `.env.example`. Для общей NAT-сети учитывайте суммарный поток клиентов. Блокировка конечна; состояние ограничено 10 000 действующими IP-бакетами. При заполнении новые IP получают временный 429 до освобождения места.

## Персональные данные

Перед публикацией заполните `LEGAL_OPERATOR_NAME`, `LEGAL_OPERATOR_ADDRESS`, `LEGAL_OPERATOR_EMAIL`, `STORE_PHONE` и контакты магазина. Политика доступна по `/privacy`. Checkout требует отдельного согласия; его факт, версия политики и время сохраняются в заказе и CSV. При существенном изменении текста политики меняйте `PRIVACY_POLICY_VERSION`. Текст политики требует проверки под конкретного оператора и процессы магазина.

`/admin`, CSV и страницы заказа отправляют `Cache-Control: no-store`; у страницы заказа также `Referrer-Policy: no-referrer` и запрет индексации. Ссылки заказа остаются случайными bearer-ссылками без нового срока истечения; передавайте их приватно.

## Резервная копия, миграция и откат

Runtime-данные: `data/shop.db`, `data/media`, `data/imports`. Остановите все web/CLI-писатели и выполните команду с новым каталогом назначения вне `data`:

```bash
docker compose -f docker-compose.prod.yml stop shop
python scripts/backup_data.py --data-dir data --destination ../tigr-backup-2026-09-10
```

Скрипт использует SQLite backup API (включая подтверждённые WAL-записи), проверяет целостность, копирует media/imports, отвергает symlink и не перезаписывает существующий backup. Маркер `BACKUP_COMPLETE` появляется только после успеха. Отдельно сохраните `.env` и конфигурацию Caddy в защищённом месте; backup содержит персональные данные. На Windows проверьте ACL backup и `.env`.

Миграция выполняется автоматически и добавляет таблицы административных сессий, служебного состояния, rate limiting, идемпотентности и outbox. Старые товары, заказы, позиции, public_token и согласия не удаляются и не переписываются; недостающие в очень старых БД поля согласия добавляются совместимо. Проверка/ALTER сериализованы между worker.

Для отката остановите все процессы, сохраните текущий `data` отдельной копией, восстановите согласованный backup в подготовленный каталог и верните соответствующую версию приложения/конфигурации. Не смешивайте старый `shop.db` с WAL/SHM другой версии. Восстановление старого backup теряет более новые заказы, если их предварительно не перенести. Возвращение исходного уязвимого кода в публичный доступ снова открывает устранённые проблемы; оставляйте такой диагностический откат недоступным извне.

## Проверки и обновления

```bash
python -m pip install --require-hashes -r requirements-dev.lock
python -m pip check
python -m pytest -q
python -m compileall -q app.py shop scripts
python -m pip_audit --require-hashes -r requirements.lock
python -m bandit -r shop scripts app.py
python scripts/scan_secrets.py --history
docker build -t tigr-security-check .
```

При наличии проверенного Caddy 2.11.4 выполните `python scripts/check_caddy.py --binary /путь/к/caddy`. Проверка использует временные loopback-listeners и синтетический upstream, проверяет реальные 413/502 и заголовки с Content-Length/chunked. Дополнительный `python scripts/check_caddy_uvicorn.py --binary /путь/к/caddy` запускает временную цепочку Caddy → Uvicorn и проверяет health/read-header timeout. TLS и production-трафик не затрагиваются.

`requirements.in` задаёт прямые зависимости; `requirements.lock` фиксирует весь runtime-граф с хешами. Dev-граф согласован с runtime через constraint. Для обновления проверенной версией `uv==0.11.17`:

```bash
uv pip compile requirements.in --python-version 3.12 --universal --generate-hashes --output-file requirements.lock --no-header --no-annotate --no-config
uv pip compile requirements-dev.in --python-version 3.12 --universal --generate-hashes --constraint requirements.lock --output-file requirements-dev.lock --no-header --no-annotate --no-config
```

После обновления прогоните обе версии Python, аудит и контейнерные проверки. CI использует read-only permissions и полные SHA Actions; Dependabot проверяет Python, Docker и Actions еженедельно. Результаты и невыполненные проверки второго прохода перечислены в [SECURITY_AUDIT_R2.md](SECURITY_AUDIT_R2.md). Инструкция по публикации репозитория: [GITHUB_UPLOAD.md](GITHUB_UPLOAD.md).
